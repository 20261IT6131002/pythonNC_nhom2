Status: **Proposed for M1/M3/M4 review**, implemented on the user's instruction.
No OPEN SRS decision is promoted to approved. Base: `develop@60f6085` (PR #15).
Plan: [R1 next execution plan](R1_NEXT_EXECUTION_PLAN_FR17_FR14.md), sections 6–7 and 36.
ADR: [R1 secure storage](../../adr/ADR_R1_SECURE_STORAGE.md).

Scope: R1-02.1..4 only. This foundation supports FR-17/AC-17b, FR-14/AC-14a/b,
NFR-SEC-02/04, NFR-MAIN-01 and BR-12/14. It does not implement autosave, recovery,
locked-note UI, a KDF, Mongo schema changes or production key provisioning.
R1-03 starts from develop after R1-02 integration; R1-04 follows R1-03.

## Decisions used for implementation

| ID | Contract |
| --- | --- |
| SEC-D01 | AES-256-GCM; exactly 32-byte keys. No algorithm downgrade. |
| SEC-D02 | Each encryption obtains a fresh 12-byte nonce from the OS CSPRNG; callers cannot supply/reuse one for encryption. |
| SEC-D03 | FR-14 will require fresh 16-byte KDF salts; no passphrase/KDF behavior is implemented here. |
| SEC-D04 | KDF algorithm, cost, privacy and lock lifecycle stay open until the FR-14 contract. |
| SEC-D05 | Secrets use Windows Credential Manager, macOS Keychain or Linux Secret Service through explicitly selected keyring backends. |
| SEC-D06 | Backend unavailable, denied, corrupt or unacknowledged: raise a typed error; never create a fallback file/key or return a fabricated secret. |
| SEC-D07 | Exceptions and result codes contain fixed messages; key, plaintext, ciphertext, backend details and AAD are not logged. |

## Public boundary

- `ContentCipher.encrypt(plaintext: bytes, key: bytes, aad: bytes) -> EncryptedEnvelope`.
- `ContentCipher.decrypt(envelope: EncryptedEnvelope, key: bytes, aad: bytes) -> bytes`.
- `SecretStore.get(name: str) -> bytes | None`: None means a successful native read
  found no entry, not that a backend failed.
- `SecretStore.put(name: str, secret: bytes) -> None`: native write and readback must
  agree before acknowledging success. Replacing an existing named value is explicit.
- `SecretStore.delete(name: str) -> None`: missing is idempotent; failed native deletion
  is reported. No enumeration or access outside the app's service namespace.

The immutable `EncryptedEnvelope` contains `format_version=1`, `algorithm="AES-256-GCM"`,
`nonce` and `ciphertext` (including a 16-byte authentication tag). Byte fields have
`repr=False`; unsupported versions/algorithms, wrong types, non-12-byte nonce and
truncated tags are rejected. Keys never enter the envelope.

## Authentication and serialization

AAD must be nonempty bytes identifying the consumer and record. The adapter prefixes
it with `noteapp:envelope:v1:AES-256-GCM\0`, so version/algorithm context and caller AAD
are authenticated together. A future draft caller must use a distinct stable context
from a locked-note caller. This task does not invent either record identity policy.
Wrong key, altered ciphertext/tag/nonce and wrong AAD produce the same
`AuthenticationFailed` outcome, with no partial plaintext.

Infrastructure serializes only the four envelope fields as UTF-8 JSON with strict
base64 byte fields. Unknown/extra/duplicate fields, invalid JSON/base64 and unsupported
metadata are rejected. No pickle, object deserialization, implicit encryption or file
I/O occurs in the serializer. A future file adapter owns payload bounds/atomic writes.

`SecretStore` names use `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}` and are metadata, not titles.
Values are 1–512 bytes (a portable key-material bound, not a note-content limit),
stored as version-prefixed base64 only inside native OS secure storage. Base64 is a
binary encoding, not encryption; OS protection is essential. Missing keys are never
regenerated by this adapter. R1-03 must decide creation/concurrency/rotation policy.

## Error and lifecycle behavior

- Invalid caller input/envelope: `ValidationError` / `ErrorCode.VALIDATION`.
- Authentication/integrity failure: `AuthenticationFailed` /
  `ErrorCode.AUTHENTICATION_FAILED`.
- Crypto/native-secret provider failure: `SecureStorageUnavailable` /
  `ErrorCode.SECURE_STORAGE_UNAVAILABLE`.

Constructing the secret adapter is side-effect free; native access is lazy. Callers
must invoke crypto, keyring and any future file I/O through the existing worker pool.
No bootstrap wiring is added before the first real draft/lock use case needs it.
Keyring auto-selection, configured plugins, null/file backends and plaintext fallback
are excluded. Python immutable bytes cannot promise reliable memory zeroization.

## Acceptance and release gates

Tests cover SEC-U01..07, SEC-K01..03, malformed envelopes, secret-safe repr/error
mapping, native backend selection, provider failure and readback verification.
Contract tests reuse a deterministic fake secret store and the real adapter with an
injected native test double. Native Windows credential smoke uses a unique synthetic
credential, removes only that entry, and is opt-in outside CI.

Existing regression suites and packaging smoke must still pass. Local results do not
establish remote CI or OS support not exercised. M1/owners and an independent security
review remain merge/release gates. Revert the grouped commits to roll back; no Mongo
migration, real draft files or application encryption keys are introduced.
